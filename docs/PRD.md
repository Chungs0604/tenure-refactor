## 1. 한 줄 정의

**"입었던 기록을 남기고, 판매할 때 옷의 가치를 보여주다"** — OOTD 착용 기록으로 옷의 가치를 증명하는
패션 C2C 거래 서비스.

OOTD 사진을 올리면 사진 속 옷에 아이템 태그가 붙는다. 그 태그가 쌓여 아이템의 **실착 이력**이 되고,
판매 시점에 이 이력이 상품 가치의 근거가 된다. 거래가 끝나면 기록은 구매자에게 승계된다.

일반적인 중고거래 앱은 "상품"이 거래마다 새로 생기는 게시글이다. Tenure는 다르다 — **아이템은 거래를
넘어 존속하는 개체**이고, 판매 등록은 그 아이템에 붙었다 떨어지는 부속물이다. 이 축이 다른 모든
설계 결정(소유 이력 append-only, soft delete 금지 대상 등)의 근거다. 상세 근거는 `erd.md` §1.

## 2. 핵심 사용자 흐름

```
OOTD 게시 ──(태그)──▶ 아이템 실착 이력 축적 ──▶ 판매 전환 ──▶ 구매 제안/거래 의사
                                                                    │
                                        결제 승인(임시) ──▶ 판매자 수락 ──▶ 최종 결제
                                                                    │
                                   상품 발송 ─▶ 배송 완료 ─▶ 구매 확정(72h 자동) ─▶ 정산
                                                                    │
                                                        item_ownership 승계 → 기록은 구매자에게
```

- **결제가 주문보다 먼저 생긴다.** 제안 시점에 결제 승인이 임시로 잡히고, 판매자가 수락해야
  `trade_order`가 생긴다. 거절·취소·만료 시 승인이 해제된다. 상세: `erd.md` §1.2
- 채팅은 아이템 단위로 열리고, 거래 단계별 CTA가 채팅방 안에 붙는다(SCR-042)

## 3. 기능 범위

47개 화면 기준 그룹. 각 화면의 상세 엔티티·액션은 `erd.md` §4 화면 인벤토리가 정본이다.

| 그룹 | 포함 기능 |
|---|---|
| 계정 | 가입·로그인·비밀번호 찾기, 프로필(닉네임·성별·키·몸무게), 배송지·정산 계좌 관리, 알림 설정, 팔로우, 차단·신고, 회원탈퇴 |
| OOTD / 아이템 | 홈 피드, OOTD 촬영·게시(AI 태그 부착), 아이템 등록·수정, 아이템 히스토리(실착 이력), 마이페이지 |
| 판매 / 거래 | 판매 전환, 대표 OOTD 선택, 위시리스트, 구매 제안/거래 의사, 결제, 거래 상세·타임라인, 운송장 입력, 판매·구매 내역 |
| 채팅 / 알림 / 검색 | 아이템별 채팅방, 알림 목록, 검색(게시물·계정 탭, 필터) |

## 4. 구현 현황

**확인 기준: 컨트롤러 존재 여부, 2026-10-11 재확인.** 이 섹션은 기능이 추가될 때마다 바로 낡는다 —
도메인을 새로 시작하기 전에 `find src/main/java/com/tenure/domain -iname "*Controller.java"`로 먼저
재확인할 것. **예외: `payment`는 설계상 단독 컨트롤러를 두지 않고 `offer`/`order` 플로우에 내장되므로
이 기준에 걸리지 않는다 — 구현 여부는 `PaymentService`(승인·확정·해제·환불) 존재로 판단한다.**

- **완료**: `auth` · `user` · `address` · `payout` · `category` · `post` · `item` · `listing` ·
  `offer` · `order` · `payment`(offer/order 플로우에 내장) · `chat` · `notification` · `wishlist` ·
  `follow` · `block` · `report`
- **미착수**: `search`(엔티티만 존재, API-200~207)
- **전용 API 없음**: `settlement` — API-165(구매 확정)가 내부에서 자동 생성하는 구조라
  별도 컨트롤러를 두지 않는다(`api-spec.md` §3 CRUD 커버리지 참고). 구현 대상에서 빠지는 게
  아니라 애초에 단독 엔드포인트가 없는 도메인이다.

`notification` 은 발행(`notify`/`notifyAll`)·조회·읽음 처리·수신 설정까지 전부 구현됐다.
`listing` 이 가격 변경·판매 완료·판매 중 재전환 때, `follow` 가 팔로우 시점에 발행하는 훅도
들어갔다 — 팔로우 알림은 기존 탭 4종 어디에도 안 맞아 `NotificationCategory.ACTIVITY` 를
새로 추가했다(2026-10-11, `design-audit.md` N-4 참고).

회원탈퇴(`API-016`)도 구현 완료다(2026-10-08, `feat/user-withdrawal`). 즉시 익명화 +
대기 중 제안 정리(`OfferService.cancelAndRejectPendingForWithdrawal`) + 연관 데이터(배송지·정산계좌·
검색기록·알림·알림설정) 하드 삭제로 끝난다. 처리 규칙 전체는 `erd.md` §8 DEC-004 참고.

다음 착수 후보와 선결 사항은 `docs/design-audit.md` 끝의 🚦 절을 먼저 확인한다 — `listing` 때도
`DEC-005` 같은 선결 결정이 있었다.

## 5. 범위 밖 (의도적 보류)

설계 단계에서 제외했거나 별도 도메인 구현 시점으로 미룬 것. 빠뜨린 게 아니라 **확정된 결정**이다.
각 항목의 전체 근거는 `erd.md` §8 또는 해당 메모리를 참고.

- **AI 아이템 인식** — 감지 영역·후보 목록·신뢰도는 저장하지 않는다. 사용자가 확정한 태그만
  영속화하고, AI는 외부 서비스로 본다
- **태그 수정 이력**(`post_tag_edit_log`) — 정의만 하고 MVP 외
- **관리자 기능** — 신고 접수 후 게시물·아이템을 내리는 운영 흐름. `report`는 접수까지만 담는다
- **공지사항 · 문의하기** — 관리자 기능이 범위 밖이라 쓸 주체·답할 주체가 없다. 정적 페이지로 처리
- **탈퇴 후 재가입 시 제안 기회 초기화 방지** — 막으려면 탈퇴자 식별 정보를 보관해야 해 즉시 익명화
  원칙과 충돌한다. 알고 넘어간다
- **미결**: 소셜 로그인(구글·네이버) 설계 반영 여부, 인증번호 재전송 정책(쿨다운·일일 한도),
  카테고리별 사이즈 체계 매핑 — `erd.md` §8 Q6·Q7, `design-audit.md` Q-1·Q-2
