# 설계 감사 — 피그마 화면 ↔ schema.yaml ↔ api-spec.md

## 왜 하는가

`schema.yaml` 은 피그마의 **텍스트 레이어 덤프**에서 생성됐다(`erd.md` §9). 그런데 피그마는
**컴포넌트 인스턴스 내부를 덤프에 펼치지 않는다.** 라디오·배지·행별 버튼·토글처럼 컴포넌트로
묶인 UI 는 한 글자도 잡히지 않았고, 그 자리는 `source: inferred` 로 채워졌다.

`api-spec.md` 는 `schema.yaml` 만 읽어 생성되므로 이 누락을 교정할 기회가 구조적으로 없다.
그래서 **화면을 직접 보고** 세 문서를 맞추는 작업이 이 감사다.

실제로 정산 계좌에서 이 경로로 3건이 드러났다(기본 지정 API 누락, 등록 요청의 `isDefault`,
근거 없는 계좌번호 마스킹). 같은 사고가 남은 도메인에서 반복되는 것을 막는 것이 목적이다.

- 범위: 47개 화면 전체
- 방법: 섹션별 스크린샷을 직접 판독 → `schema.yaml`·`api-spec.md` 와 대조
- 표기: **A**=조치 필요 · **Q**=결정 필요 · **OK**=일치

## 묶음 1 — 계정 (SCR-001 ~ SCR-010)

판독한 화면: 온보딩·회원가입 20프레임·비밀번호 찾기·배송지 관리·정산 계좌 관리·알림 설정·
로그인 정보·회원탈퇴·로그아웃·환경 설정

### Q-1. 가입 플로우에 실명·휴대폰 입력 화면이 없다 (최우선)

회원가입은 4단계다 — 계정 생성(이메일·비밀번호·비밀번호 확인) → 동의 → 주소 등록 → 프로필 작성
(사진·닉네임·성별·키·몸무게). **실명과 휴대폰번호를 받는 화면이 없다.**

그런데 `user.real_name`·`user.phone` 은 **NOT NULL** 이고, 로그인 정보 화면(SCR-004)은
`홍길동` / `821012345678` 을 **표시**한다. 값이 어딘가에서는 와야 한다.

가입 중 주소 등록(`2791:17337`)도 **주소 + 상세 주소만** 받는다 — 수령인·연락처·우편번호가 없다.
반면 `shipping_address` 는 셋 다 NOT NULL 이고, 배송지 관리의 '배송지 추가' 화면에는 셋 다 있다.

현재 구현된 `API-012` 는 `realName`·`phone`·`address.recipientName`·`address.phone`·
`address.zipcode` 를 전부 필수로 받는다 — **화면만으로는 가입이 불가능하다.**

### Q-2. 소셜 로그인(구글·네이버)이 설계에 없다

로그인 화면(`2791:15250`)의 `다음` 구분선 아래에 구글·네이버 아이콘이 있다.
`schema.yaml` 에 provider 컬럼이 없고, `api-spec.md` 에 엔드포인트가 없고,
`design_exclusions` 에 제외 근거도 없다 — **누락이다.**

Q-1 과 연결된다: 소셜 제공자가 실명·휴대폰을 주므로 이메일 가입에만 입력 화면이 필요할 수 있다.

### A-1. 알림 설정 — 토글 9종 3그룹인데 스키마는 4종이다

화면(`3063:28457`)의 토글과 기본값:

| 그룹 | 항목 | 기본값 |
|---|---|:--:|
| 필수 | 거래 요청 / 요청 상태 / 요청 자동 취소 / 거래 상태 | 전부 ON |
| 활동 알림 | 채팅 알림 / 관심 아이템 | ON |
| 활동 알림 | 팔로우 알림 | OFF |
| 서비스 알림 | 서비스 소식 / 혜택 및 마케팅 | OFF |

`notification_setting.category` 는 `NotificationCategory`(ACTION_REQUIRED·ITEM_NEWS·
TRADE_STATUS·WISHLIST)를 재사용한다. 그런데 그 enum 은 **알림 목록 화면(SCR-044)의 탭**이다.
설정 토글과 목록 탭은 **다른 축**인데 한 enum 을 공유하고 있다.

→ `NotificationSettingType` enum 9종을 신설하고 `category` 와 분리한다. 항목별 기본값도 명세에 적는다.
→ `혜택 및 마케팅` 은 광고성 정보 수신이라 동의 시각 기록이 필요한지 확인해야 한다(§Q-4).

### A-2. 회원탈퇴 사유가 드롭다운 4종이다

화면(`3063:29262`)은 자유 입력이 아니라 select 다.

```
사용 빈도가 낮아요. / 원하는 아이템을 찾기 어려워요.
다른 서비스를 이용할 예정이에요. / 거래 경험이 만족스럽지 않았어요.
```

`user_withdrawal.reason` 은 `VARCHAR(500)` 자유 텍스트다. 은행명과 같은 유형의 오류다.
→ `WithdrawalReason` enum 4종 + `VARCHAR(40)`. '기타(직접 입력)' 옵션이 있는지는 미확인.

### A-3. 배송 요청사항도 드롭다운이다 — **구현된 코드에 영향**

배송지 추가 화면(`4245:46588`)의 `배송 요청사항(선택)` 은 select 다.

```
문 앞에 놓아주세요. / 경비실에 맡겨주세요. / 택배함에 넣어주세요. / 직접 입력
```

`직접 입력` 을 고르면 텍스트 필드가 열리고 **`최대 50자까지 입력 가능`** 이 뜬다.

현재 `shipping_address.delivery_request` 는 `VARCHAR(255)` 자유 텍스트이고 구현도 그렇다.
→ 요청 유형 enum + 직접 입력 50자 구조로 바꾼다. `order_shipment` 스냅샷도 같이 바뀐다.

### A-4. DEC-005 의 전제가 사실과 다르다 — 설정 화면은 이미 있다

DEC-005 는 "설정의 기본 배송비 기능을 제외한다. **재검토 시점: 설정 화면이 디자인되면**" 이다.
설정 화면(`3063:28991`·`2958:72226`)의 `거래` 섹션에 메뉴가 **셋** 있다.

```
배송지 관리 · 정산 계좌 관리 · 기본 배송비 · 수수료 부담 기본값 · 구매 제안 받기 기본값
```

메뉴만 있고 상세 화면은 아직 없다. 하지만 이 값들은 `item_listing`·`purchase_offer` 의
기본값으로 쓰이므로 **listing·offer 도메인 설계 전에** 결론이 나야 한다.
현재 "미판매 아이템 구매 제안의 배송비는 항상 0원" 제약이 DEC-005 에 기대고 있다.

### Q-3. 설정 > 서비스 메뉴에 대응 엔티티가 없다

```
공지사항 · 문의하기 · 약관 · 개인정보 처리방침 · 버전 정보
```

`약관`·`개인정보 처리방침`·`버전 정보` 는 정적 페이지로 충분하다.
`공지사항`·`문의하기` 는 저장이 필요할 수 있는데 엔티티도, 제외 근거도 없다.

### Q-4. 인증번호 재전송 정책이 없다

비밀번호 찾기·회원가입 모두 인증번호 입력 옆에 `재전송` 버튼이 있다.
쿨다운·1일 발송 한도가 명세에 없다. DEC-009 는 "어뷰징 추적이 필요해지면 재검토" 로 미뤄뒀지만
**버튼이 화면에 있다.**

### OK — 화면과 일치한 것

- **로그인 정보**(SCR-004) — 이름·휴대폰번호·계정 이메일 3행 읽기 전용. `API-013` 과 일치
- **프로필 수정**(SCR-005) — 사진·닉네임·성별·키·몸무게. 사진만 선택. `API-015` 와 일치.
  키·몸무게가 슬라이더라 범위 제약이 필요하다(검색 필터 기준 0~200cm·0~150kg)
- **약관 동의** — 필수 3종뿐. 마케팅 동의는 이 단계에 없다. `AgreementType` 3종 유지
- **비밀번호 찾기** — 이메일 → 인증번호 → 새 비밀번호 + 확인. `API-004`·`005`·`006` 과 일치
- **배송지 관리** — 기본 배송지에만 삭제 버튼이 없다. 구현과 일치.
  다만 기본 변경이 '클릭 즉시' 가 아니라 **라디오 선택 + 하단 `변경하기`** 다(정산 계좌와 동일).
  엔드포인트 모양은 그대로여서 코드 영향은 없다
- **정산 계좌 관리** — 이번 작업에서 반영 완료

### 코드 후속 조치 (감사 완료 후 일괄)

이미 구현된 도메인에 영향이 가는 항목이다. **문서를 다 맞춘 뒤 한 번에 반영한다** —
감사 중간에 고치면 뒤 묶음에서 또 바뀔 수 있다.

- `ShippingAddress` — `deliveryRequest` 자유 텍스트(255) → `DeliveryRequestType` + 50자. 엔티티·DTO·마이그레이션·테스트
- `User` — `provider`·`providerId` 추가, `passwordHash` nullable. 마이그레이션
- `AuthService` — `API-007` 소셜 로그인, `signupToken` 발급·검증
- `UserService` — `API-012` 의 소셜 가입 분기
- `notification_setting`·`user_withdrawal` — 아직 구현 전이라 코드 영향 없음

## 묶음 2 — 게시물 · 소셜 (SCR-011 ~ SCR-021)

판독한 화면: 홈 피드·OOTD 상세·태그된 아이템 목록·OOTD 게시물 올리는 과정·게시물 더보기 옵션·
마이페이지·타인 프로필·팔로워/팔로잉·신고 사유 드롭다운

### Q-5. `post.content` 는 근거가 없다

게시물 작성 플로우 어디에도 **본문 입력란이 없다.**
촬영 → 비율 선택(1:1·3:4·4:5) → 날짜 선택 → 아이템 태그 → 게시물 미리보기 → `게시하기` 로 끝난다.
`게시물 미리보기`(`3380:33759`)의 버튼은 `태그 수정` 과 `게시하기` 둘뿐이고,
OOTD 상세(`2791:26077`)에도 본문을 그리는 영역이 없다 — 사진·태그·좋아요/저장·작성자 줄이 전부다.

`schema.yaml` 의 근거는 이렇게 적혀 있다.

```
content: 게시물 본문. 예 '안녕하세요 SSU님!'
```

**그런데 `안녕하세요 SSU님!` 은 홈 화면 헤더의 인사말이다**(`2791:21678`). 게시물 본문이 아니다.
화면에서 텍스트를 가져오면서 출처를 잘못 붙인 것이다.

### A-5. 알림 안읽음 배지를 읽을 API 가 없다

홈 헤더의 벨 아이콘에 **빨간 점**이 붙어 있다(`2791:21678`). 마이페이지 헤더에도 같은 벨이 있다.
`ix_notification_unread(user_id, read_at)` 인덱스는 만들어 뒀는데 **그 인덱스를 쓰는 엔드포인트가 없다.**
알림 목록(`API-190`)을 통째로 받아 세는 것은 홈 진입마다 하기엔 무겁다.

→ `GET /api/v1/notifications/unread-count` 를 추가한다.

### A-6. 팔로우 탭 상단의 팔로잉 사용자 가로 목록이 없다

홈 `팔로우` 탭 상단에 팔로잉 사용자의 프로필이 **가로 스크롤 목록**으로 붙는다(선택 시 테두리 강조).
`API-070` 의 응답에도, 별도 API 에도 없다. `API-051`(팔로잉 목록)로 채울 수 있으나
화면 단위가 다르므로 명세에 연결을 적어야 한다.

### A-7. 태그된 아이템 행에 위시 상태가 빠져 있다

목록 행마다 우측에 위시(북마크) 아이콘이 있고 등록 여부로 상태가 갈린다.
`API-079` 응답에 `isWished` 가 없다.

### A-8. 신고 사유가 대상 종류별로 다르다

드롭다운을 펼친 화면에서 확인한 실제 목록이다.

| 대상 | 사유 |
|---|---|
| 게시물 | 사람이 직접 착용한 OOTD가 아님 · 부적절하거나 유해한 이미지 · 도용한 사진 또는 권리 침해 · 광고 또는 반복 게시물 · 개인정보 노출 · 서비스와 관련 없는 게시물 |
| 상품 | 가품 또는 정품 의심 · 상품 정보가 실제와 다름 · 도용한 사진 또는 권리 침해 · 사기 또는 외부 거래 유도 · 거래 금지 품목 · 부적절한 이미지 또는 내용 |

`ReportReason` 10종은 이 둘의 **합집합**이라 값 자체는 맞다. 다만 **대상별로 고를 수 있는 사유가
다르다는 제약이 어디에도 없다** — 게시물에 `가품 의심` 을 붙일 수 있는 상태다.
사용자 신고(`USER`, 채팅에서 진입)의 사유 목록은 아직 확인하지 못했다 → 묶음 4 에서 본다.

### A-9. 타인 게시물 목록도 월 그룹이다

타인 프로필의 게시물 그리드에도 `6월`·`5월` 월 헤더가 붙는다. `API-082` 에는 그 언급이 없다
(`API-081` 에는 있다).

### Q-6. 태그된 아이템 화면 하단의 추천 섹션에 API 가 없다

`관련된 OOTD 보러가기` 아래로 추천이 4블록 붙는다.

```
비슷한 무드 모아보기 · Levis / LVC 1955 501과 비슷한 스타일
Guidi / 788z Boots와 비슷한 스타일 · 함께 참고하기 좋은 코디
```

`API-202`(추천 섹션)는 **검색 화면**의 추천이라 단위가 다르다. 아이템 기준 추천 API 가 없다.

### OK — 화면과 일치한 것

```
추천 순 ✓  ·  최신 순  ·  좋아요 순  ·  조회수 순  ·  저장 순
```

`api-spec` 은 `sort: 관련도 (미정)` 로 비워 둔 채였다. 더 큰 문제는 **`조회수 순` 이 없는 컬럼을
요구한다**는 것이다 — `post` 에 `view_count` 가 없었다.

→ `post.view_count` 를 추가하고, 조회는 Redis `post-view:{postId}` 에 `INCR` 로 모았다가
주기 배치가 컬럼에 더한다(`DEC-019`). 조회마다 UPDATE 하면 인기 게시물 한 행에 쓰기가 몰리고
읽기 경로에 락 경합이 생긴다 — `DEC-014` 가 최근 열람을 Redis 로 옮긴 것과 같은 기준이다.

### Q-11. `추천 검색어` 칩이 명세에 없다

검색창을 누르면 최근 검색 위에 칩이 뜬다 — `데님 팬츠` · `나이키 신발` · `Levis 501` · `가죽 자켓`.
`API-203` 은 최근 검색어와 최근 본 사용자만 담고 있었다.

→ `API-206` 신설. **`search_history` 집계**로 채운다(`DEC-020`). 운영 고정 목록 테이블은
관리자 기능이 범위 밖이라 값을 넣을 화면이 없어 배제했다. 초기에는 빈 배열이 내려간다.

### A-20. 알림 행에 썸네일이 있는데 담을 컬럼이 없다

알림 목록(`2958:68634`)의 행마다 아이템 사진이 붙는다. `notification` 은 **다형 참조**라
대상 테이블과 조인할 수 없다 — 값을 가져올 방법이 없었다.

→ `notification.image_key` 를 추가해 발행 시점에 스냅샷한다.

덧붙여 `title` 의 용법도 달랐다. 명세 예시는 `GilDong 님이 구매 제안을 보냈습니다!` 였는데

### A-21. 추천 섹션의 `더보기` 에 API 가 없다

검색 메인의 추천 4블록에 각각 **오른쪽 화살표**가 있고, 누르면 그 섹션만 모은 전체 목록이 열린다
(`검색 섹션에서 추천에 따른 상세페이지`). `API-202` 는 섹션 묶음만 주고 페이징이 없다.

→ `API-207 GET /search/recommendations/{section}` 신설.
`POPULAR_USER` 만 응답이 `users[]` 이고 나머지 셋은 `posts[]` 다.

### A-22. 알림 목록은 날짜 헤더로 묶인다

`어제` · `10월 24일` 로 그룹이 나뉜다. `API-190` 에 언급이 없어 정렬·그룹 기준을 적었다

## 재검증 — 고친 스킬의 체크리스트를 다시 돌렸다

감사를 마친 뒤 `figma-to-erd`·`erd-to-api-spec` 스킬에 빠져 있던 단계를 채웠고,
**그 새 체크리스트로 이 문서들을 다시 검사했다.** 3건이 더 나왔다.

### R-1. 선택지 드롭다운에 기준이 없었다

새 체크리스트의 `선택지 드롭다운 → 선택지 목록을 내려줄 API` 항목이 잡았다.
은행 목록(`API-035`)은 만들었는데 **같은 성격인 택배사는 빠져 있었다.** 기준 없이 그때그때 정한 탓이다.

기준을 세웠다(`DEC-021`) — **값이 앱 배포와 무관하게 늘어나는가.**

| | 판정 | 이유 |
|---|---|---|
| `BankCode` · `CourierCode` | **API 로 내린다** | 서버가 값을 더해도 앱이 못 따라오면 화면이 낡는다 |
| `Gender` · `FeeBearer` · `PaymentMethod` · `ConditionCode` · `DeliveryRequestType` · `WithdrawalReason` | 클라이언트가 갖는다 | 값이 고정이고 문구가 디자인에 박혀 있다 |
| `NotificationSettingType` | **문구를 함께 내린다** | 값은 고정이지만 두 줄짜리 문구 9개를 복제하면 문구 수정이 배포에 묶인다 |

→ `API-167`(택배사 목록) 신설, `API-040` 응답에 `group`·`title`·`description` 추가.

### R-2. `inferred` 5건이 "확인했는지" 구분되지 않았다

`딥링크 대상 종류` 처럼 짧은 `evidence` 는 **화면을 보고 없다고 판단한 것인지,
아예 안 본 것인지** 구분되지 않는다. 다섯 건 모두 "왜 화면에 없는지"를 적어 보강했다.

넷은 **화면에 없는 것이 맞다**(상태 컬럼·등급 이력·무효화 사유). 하나(`notification.target_type`)만
디자인 확정 시 대조가 필요한 **확인 필요**로 남겼다.

### R-3. `erd.md` 선두에 「화면 미확인 항목」이 없었다

새 스킬이 요구하는 §0 을 만들었다. 말미의 §8 `확인 필요`(설계 판단이 갈린 것)와 성격이 달라
섞지 않는다 — §0 은 **화면을 덜 본 것**이다.

### 한계로 남긴 것

`evidence` 의 노드 ID 표기는 **재판독한 항목에만 있다**(`design` 필드 194개 중 13개).
전수 소급은 화면을 다시 다 봐야 해서 하지 않았고, 그 사실을 `erd.md` §0 에 적었다.
스킬에도 "기존 문서 보강 시 소급하지 않는다"를 명문화했다.

### 재검증 후 수치

- 엔드포인트 **103개 → 104개**(`API-167`)
- 설계 결정 **26 → 27건**(`DEC-021`)
- `erd.md` 에 §0 신설

## 잔여 9개 섹션 판독 — 전 화면 커버리지 달성

재검증에서 "본 감사가 37개 섹션 중 28개만 열어봤다"가 드러나 나머지를 마저 읽었다.
**2건이 더 나왔다.** 둘 다 이미 명세가 있던 엔드포인트의 **응답 구조 오류**다.

### G-1. 거래 상세의 `배송 조회` 버튼에 대응이 없다

거래 상세(`2958:63661`) 배송지 섹션 우측에 `배송 조회` 버튼이 있다(운송장 입력 전에는 비활성).
`API-160` 은 `courierCode`·`trackingNo` 만 내려줘서 **버튼이 어디로 가는지** 알 수 없었다.

→ `shipment.trackingUrl` 추가. 택배사별 추적 URL 패턴을 클라이언트가 가지면 택배사 추가가
앱 배포에 묶이므로 **서버가 조합해 내려준다**(`DEC-021` 과 같은 기준). URL 은 저장하지 않는다 —
`courier_code` + `tracking_no` 로 만든다.

### G-2. 채팅방 헤더 CTA 가 버튼 하나가 아니다

`API-182` 는 `cta` 를 **문자열 하나**로 내리고 예시가 `상품 상세 / 구매하기 / 거래 상세` 였다.
실제로는 **버튼이 둘**이고 라벨이 세 축으로 갈린다.

| 축 | 값 |
|---|---|
| 판매 상태 | 판매 중 `상품 상세`·`상품 관리` / 미판매 `아이템 상세`·`아이템 관리` |
| 역할 | 구매자 `…상세` / 판매자 `…관리` |
| 거래 단계 | 제안 전 `구매하기` / 응답 대기 `보낸 요청 보기`·`요청 확인` / 거래 후 `거래 상세` |

게다가 **비활성 상태**가 있다 — `구매제안 O` 로 열린 방에서 판매자가 `구매제안 X` 로 바꾸면
`제안 확인` 이 회색으로 죽는다(피그마 주석에 그 경우가 따로 그려져 있다).

→ `ctas[]` 배열로 바꾸고 `label`·`action`·`targetId`·`enabled` 를 내린다.
라벨 조합이 여덟 가지라 클라이언트가 분기를 복제하면 어긋난다.

### 경미

- 택배사 표기가 화면마다 다르다 — 선택 화면은 `CJ대한통운`, 거래 상세는 `CJ 택배`.
  저장값은 같고 표시 문구만 다르다. `CourierCode` evidence 에 적어 뒀다

### 일치 확인된 것

- **거래 상세** — 타임라인 5단계와 각 날짜, `거래 취소` 가 결제 완료 단계에만,
  구매자·판매자 정보 **둘 다** 표시, 정산 정보(정산 계좌 포함). `API-160` 과 일치
- **운송장 입력** — 택배사 4종(`CJ대한통운`·`우체국택배`·`GS Postbox`·`CU 편의점택배`)이
  `CourierCode` 와 정확히 일치. 한글 입력 오류·주문 없음 모달까지 있다
- **게시물 더보기** — 타인 `차단하기`·`신고하기`, 본인 `수정하기`·`삭제하기`.
  **차단은 `user_block`, 신고는 `POST`** 라 `ReportTargetType` 에서 `USER` 를 뺀 결정과 모순 없다
- **채팅 이미지 다중 전송** — 앨범에서 번호를 매겨 고르고 `전송 3` 으로 보낸다.
  `chat_message_image` 결정을 뒷받침한다
- **공유하기** — `링크 복사`·`다른 앱에 공유`·`닫기` + OS 공유 시트. 저장 대상 없다

- **회원가입 프로필 사진** — 앨범 → 원형 크롭 → 완료. `API-060` 으로 충분

## 착수를 막는 것

**없다.** 🔴 였던 `DEC-005` 가 2026-09-28 해소됐다.

| 항목 | 결정 | 결과 |
|---|---|---|
| ~~`DEC-005` 거래 기본값 3종~~ | **기능을 만들지 않고 설정 메뉴를 지운다** | `user` 에 컬럼이 붙지 않는다. `purchase_offer` 의 **"미판매 제안 배송비는 항상 0원"** 제약이 그대로 유효하다 — `listing`·`offer` 를 바로 설계할 수 있다 |
| ~~`DEC-018` 실명·휴대폰 입력란~~ | **프로필 작성 단계에서 함께 받는다** | 스키마·`API-012` 변경 없음. **디자인에 입력란 2개 추가**가 필요하다(단계 수는 안 늘어난다) |

## 도메인 구현 시점에 정하면 되는 것

| 등급 | 항목 | 시점 | 비용 |
|---|---|---|---|
| 🟡 | `Q6` 대분류별 사이즈 체계 매핑 | 프론트의 아이템 등록 화면 | seed UPDATE 1회. **백엔드는 안 막힌다** |
| 🟡 | `Q7` 인증번호 재전송 쿨다운·한도 | **배포 전** | Redis 키 1개 + `AuthService`. 제한이 없으면 메일 발송이 어뷰징 통로다 |
| 🟢 | `notification.target_type` 딥링크 대상 | `notification` 구현 시점 | **지금 정하면 오히려 손해** — 알림을 발행하는 `offer`·`order`·`chat` 을 만들며 자연히 확정된다 |
| 🟢 | `ReportTargetType.USER` 복원 | 사용자 신고 화면이 생기면 | enum 값 추가뿐 |

## 구현 순서에 따른 권고

```
post · item     →  막는 것 없음. 바로 착수 가능
                   (이 동안 소셜 자격증명 발급을 병행)
listing         →  막는 것 없음 (DEC-005 해소)
offer · order   →  미판매 제안 배송비 0원 규칙 위에서 금액 로직을 쓴다
notification    →  target_type 을 이때 확정
auth 보강       →  🟡 Q7, 소셜 로그인(자격증명 준비돼 있어야)
```

**2026-09-28 기준 착수를 막는 미결은 없다.** 남은 것은 `Q6`(사이즈 체계 매핑, 프론트),
`Q7`(재전송 정책, 배포 전), `notification.target_type`(해당 도메인 구현 시)뿐이다.
