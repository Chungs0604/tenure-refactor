# 마이그레이션 점검

`src/main/resources/db/migration/`의 변경을 커밋 전에 점검한다. 코드를 고치지 않고 발견만 보고한다.

## 절차

1. **대상 파일 모으기** — `git status --porcelain -- src/main/resources/db/migration`으로
   새로 추가됐거나(`??`, `A`) 수정된(`M`) 마이그레이션 파일을 찾는다.
   아무것도 없으면 "점검할 변경 없음"으로 끝낸다.

2. **이미 커밋된 파일 수정 여부** — 수정된(`M`) 파일 각각에 대해
   `git cat-file -e HEAD:<path>`로 HEAD에 이미 있었는지 확인한다. 있었다면 **치명** —
   체크섬이 깨져 다른 환경 빌드가 실패한다. (`protect-flyway-migrations` 훅이 Edit/Write
   시점에 막지만, 이 점검은 훅 도입 전에 수정됐거나 다른 도구로 고친 경우를 잡는다.)

3. **버전 번호 충돌** — `src/main/resources/db/migration/V*.sql` 전체에서 `V` 뒤 숫자를
   추출해 중복이 있는지 확인한다. 같은 브랜치에서 여러 커밋이 같은 다음 번호를 썼거나,
   `develop`을 나중에 머지하면서 번호가 겹치는 경우를 잡는다.

4. **네이밍 규칙** — CLAUDE.md 기준으로 새 테이블이 단수형 snake_case인지,
   `order`처럼 예약어를 쓰지 않았는지, 문자셋이 명시된 CREATE TABLE이라면
   `utf8mb4` / `utf8mb4_0900_ai_ci`인지 확인한다 (명시 안 해도 DB 기본값을 타므로
   필수는 아니다 — 명시했는데 다른 값이면만 지적한다).

5. **schema.yaml 정본과의 정합성** — 새 마이그레이션에서 만들거나 바꾸는 테이블·컬럼명을
   추출해 `docs/schema.yaml`에 같은 이름이 있는지 grep으로 확인한다. 마이그레이션에는
   있는데 schema.yaml에 없으면 **정본이 아직 안 갱신됐다**는 신호로 보고한다 — 반대로
   schema.yaml이 마이그레이션보다 앞서 있는 것(아직 적용 안 한 설계 변경)은 정상이니
   지적하지 않는다.

## 보고 형식

발견마다:
```
[심각도] 파일
무엇이 문제인가
```

심각도는 `치명`(머지 전 반드시 고쳐야 함) / `주의`(확인 필요) 둘로 나눈다.
문제가 없으면 "점검 통과"라고 보고한다.

## 하지 않는 것

- 마이그레이션 파일이나 schema.yaml을 대신 고치지 않는다
- DB에 실제로 연결해 마이그레이션을 실행하지 않는다 (`./gradlew test`의 Testcontainers가 담당)
